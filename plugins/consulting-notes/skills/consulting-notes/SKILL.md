# Consulting Notes — 미팅노트·인터뷰노트

전사본(타임스탬프 포함)을 근거로 노트를 쓰고, **모든 문장에 출처(시각·화자)를 달고 원문과 대조**한 뒤 공유용 HTML로 낸다.

> **품질의 정의**: 노트의 어떤 문장이든 클릭 한 번으로 "누가, 언제, 정확히 뭐라고 했는지" 확인할 수 있어야 한다. 원문에 없는 확정·합의·숫자는 쓰지 않는다.

## 0. 두 노트의 목적은 다르다

| | 미팅노트 (`meeting`) | 인터뷰노트 (`interview`) |
|---|---|---|
| 목적 | **논의(discussion)** — 무엇을 하기로 했는가 | **정보 수집·가설 검증** — 무엇을 새로 알게 됐는가 |
| 예 | 제안서 미팅, 고객사 미팅, 주간보고, 스티어링 | 전문가 인터뷰, 고객·유통·경쟁사 인터뷰 |
| 본문 구조 | 아젠다별 논의 내용 | Key Question별 신규 정보 |
| 결론의 핵심 | 결정사항 | 시사점(가설에 주는 의미) |
| To-do의 성격 | 담당·기한이 있는 실행 과제 | 후속 확인·추가 인터뷰 질문 |
| 추가 필수 | — | 가설 검증 표 |

두 유형 모두 **기본 정보 · Executive Summary · 본문(아젠다/KQ별) · 결론 · To-do**를 반드시 포함한다.
유형이 불분명하면 사용자에게 묻는다. 인터뷰노트라면 사전 가설 목록이 있는지도 묻는다.

## 1. 입력 확보

1. **녹음 파일만 있다** → `whisper-transcribe` 스킬로 전사해 `.json`(또는 `.srt`)을 만든다.
2. **전사본이 있다** → `.json`(Whisper 출력), `.srt`(Whisper·클로바노트), `.vtt`(Teams·Zoom, 화자 포함)를 그대로 쓴다.
3. **타임스탬프 없는 메모뿐이다** → 출처 연결이 불가능하므로 사용자에게 알리고, 녹음 또는 타임스탬프 전사본을 요청한다.
4. 기본 정보(미팅명·목적·일시·참석자)는 사용자에게 받거나 전사본에서 찾는다. **모르면 `[확인 필요]`로 두고 지어내지 않는다.**

전사본이 길면 전체를 읽되, 필요하면 `headroom` 스킬로 구간을 나눠 읽는다.

## 2. 노트 작성 (note.json)

- 스키마: `references/note-schema.md`
- 유형별 작성 규칙: `references/meeting-note.md`, `references/interview-note.md`
- 작업 폴더에 `note.json`을 만든다. **고객 정보가 담기므로 스킬 폴더나 저장소에 두지 않는다.**

핵심 규칙:
- 모든 문장에 `src`(전사본 시각 `"12:42"`, 범위 `"12:42-12:49"`, 세그먼트 `"#34"`)를 단다. 출처 없이 쓰는 해석·종합은 `"basis": "I"`로 표시한다.
- 시간순이 아니라 **아젠다/Key Question 단위**로 묶는다. Executive Summary는 결론부터 쓴다.
- 화자 구분이 없는 전사본이면 `speakers.ranges`로 구간별 화자를 문맥 추정해 넣고 `"inferred": true`로 둔다.
- 업무와 무관한 사적 대화는 노트에서 빼고 `excluded`에 시각 범위만 적는다. 공유본 스크립트에서도 가릴 구간은 `"redact": true`.
- 전사 오인식 용어는 `glossary`에 대응표로 남긴다. 스크립트 원문은 고치지 않는다.
- 처음 작성할 때는 `check` 값을 넣지 않는다. 판정은 3단계에서 한다.

## 3. 팩트체크 (필수, 건너뛰지 않는다)

```bash
python <이 스킬 폴더>/scripts/build_note.py --note note.json --transcript meeting.json --check-only --report factcheck.md
```

1. 스크립트가 출처 해석 실패, 출처 누락, **인용 원문에 없는 숫자**를 잡아낸다. 오류는 모두 고친다.
2. `factcheck.md`를 읽고 항목마다 노트 문장과 인용 원문을 대조한다. 판정 기준은 `references/fact-check.md`를 따른다.
   - 원문과 일치 → `"check": "ok"`
   - 해석이 갈리거나, 원문이 불완전하거나, 확인이 필요 → `"check": "warn"`과 `"note"`(무엇을 확인해야 하는지)
   - 원문보다 강하게 쓴 문장(제안을 합의로, 조건문을 결정으로, 질문을 약속으로)은 **문장을 원문 수준으로 고친다.**
3. 출처 범위가 핵심 발언을 빠뜨렸으면 `src`를 넓힌다. 화자 추정이 틀린 줄은 `speakers.overrides`로 고친다.
4. 서브에이전트를 쓸 수 있으면, 작성자와 다른 시각으로 보기 위해 note.json과 factcheck.md만 주고 독립 검증을 한 번 더 맡겨도 좋다.

## 4. HTML 빌드와 공유

```bash
# Artifact로 게시할 때 (Claude Code·claude.ai에서 Artifact 도구가 있으면 이쪽)
python <이 스킬 폴더>/scripts/build_note.py --note note.json --transcript meeting.json --out note.html --strict
# 파일로 공유할 때 (메일·드라이브 첨부)
python <이 스킬 폴더>/scripts/build_note.py --note note.json --transcript meeting.json --out note.html --strict --standalone
```

- `--strict`는 미검증 항목이 하나라도 있으면 빌드를 멈춘다. 최종본은 항상 `--strict`로 만든다.
- HTML 구성: 기본 정보 → Executive Summary → 본문 → (가설 검증) → 결론 → To-do → (열린 이슈) → Appendix A 전사·검증 메모 → Appendix B 스크립트 원문.
- 출처 칩(`12:42 · 화자`)을 누르면 그 자리에서 원문이 펼쳐지고, 원문 시각을 누르면 Appendix B의 해당 줄로 이동한다.
- Appendix B 스크립트는 상단 토글로 켜고 끈다. 기본은 꺼짐이며, 꺼져 있으면 보이지 않는다.
- Artifact 도구가 있으면 `note.html`을 게시해 링크를 준다. 게시물은 기본 비공개이므로, **링크 공유는 사용자가 페이지의 Share 메뉴에서 직접 켜야 한다**고 알린다.

## 5. 사용자에게 보고

- 링크 또는 파일 경로
- 항목 수와 팩트체크 결과(전사 일치 / 확인 필요)
- `확인 필요` 항목 목록과 각각 무엇을 확인해야 하는지
- 화자가 추정이라는 점, 공유본에서 가린 구간이 있으면 그 범위

## 하지 말 것

- 원문에 없는 숫자·날짜·합의를 채워 넣기
- 화자를 확정적으로 단정하기(추정이면 추정이라고 표시)
- 팩트체크 없이 `check`를 일괄 `ok`로 채우기
- 고객 녹음·노트를 스킬 폴더나 공개 저장소에 저장하기
